## 1. sudoの認識について → 正しいです

`sudo sdl.py install` のように最初からroot権限を渡しておけば、スクリプト内で`apt-get`を叩く部分もroot権限で動くので「全自動」は成立します。私の実装が誤っていました。root権限が無い状態で実行された場合は「roimを渡さず実行されたためapt導入ができません。`sudo sdl.py install`として実行してください」とエラー表示して中断する形に直します(仕様固まり次第反映します)。

## 2. submodule(vendored依存)の規模について → 調べた実数

実際に各リポジトリの `.gitmodules` や関連コミットを確認しました。「何百も」ということはなく、**20未満で収まります**。

**SDL_image (`external/`)**
デフォルトで有効な PNG/JPEG/BMP/GIF等はsubmodule不要(SDL_image自身のCコードのみ、あるいはOS側の一般的なzlib/libpngで足りる)。submoduleが要るのは「サイズが大きいため標準では入れていない」と明記されている以下の追加フォーマットのみ:
- `external/dav1d` (AV1デコーダ、AVIF用の土台。**これが一番重い**。SIMD最適化込みの本格的なコーデック実装)
- `external/libavif`
- `external/libjxl` (JPEG-XL)
- (TIFF, WebPも同様に別途用意する形だが、これらはsubmoduleというより`external/download.sh`でシステムライブラリ相当を取得する形に近い)

**SDL_mixer (`external/`)**
確認できた範囲で以下: `flac`, `libxmp`, `ogg`, `opus`, `opusfile`, `vorbis`。加えて`wavpack`, `libmodplug`, `fluidsynth`あたりも同様の位置づけと思われます。**合計でおよそ8〜10個**。ただし重要な事実として、**MP3/FLAC/Vorbisの「デフォルトバックエンド」はsubmoduleではなく、SDL_mixer自身のソースツリーに同梱されたヘッダオンリー実装(`dr_mp3` / `dr_flac` / `stb_vorbis`)です**。つまり前回私が懸念した「MP3再生にsubmoduleが必須」というのは誤りで、**MP3/FLAC/Vorbisの基本再生だけならZIP展開だけで(submodule不要で)動きます**。submoduleが要るのは「libmpg123やlibFLAC本家、libvorbis本家、Opus、MOD(libxmp)、MIDI(FluidSynth)」といった"追加/高品質バックエンド"を使いたい場合です。

**SDL_ttf (`external/`)**
`freetype`, `harfbuzz`、SVGグリフ用に`plutosvg`/`plutovg`あたりが対象。**3〜4個程度**。

**合計で見積もると、全部で15〜20個程度**。「何百も」という規模ではありません。ただし**dav1d(AV1)だけは別格に重い**(本格的な動画コーデック実装で、ソース量・ビルド時間ともに他のsubmoduleとは桁が違います)。

## 3. ダウンロード時間・ビルド時間の私の見立て

正直、実機(ラズパイ4B, 2コア, ネット回線)での実測はできないため確度は高くありませんが、経験的な目安として:

- dav1d以外の10数個のsubmodule(freetype, harfbuzz, libpng, opus, vorbis, flac, libxmp, wavpack等)は個々には小さく、ダウンロードは合計でも数十MB〜100MB程度、ビルドも2コアで合計10〜20分程度に収まると見込みます。
- **dav1dだけ**は別で、SIMDアセンブリを含む本格コーデックのため、非力な2コアCPUだと**単体で数十分かかる可能性**があります(x86でも並列ビルドで数分かかる規模のプロジェクトです)。
- fluidsynth(MIDI)はさらに別の重量級ライブラリ(独自にlibsndfileやreadline等を要求することがある)で、依存の連鎖が発生しやすく、これも時間を押し上げる要因になり得ます。

## 4. 「全機能ON」について → 前回の無断判断、申し訳ありません

ご指摘の通りで、要件を私が勝手に「動作確認に使った形式=最終要件」とすり替えていました。訂正します。方針としては次の案を提案します(選んでいただきたい):

- **案A: 全部ON。取得方法はgit clone + submodule(recursive)に変更する。**
  最も確実に「全機能」を満たせます。ただし元の要件にあった「ZIP展開」という説明とは矛盾するため、そこは仕様変更として明記が必要です。
- **案B: 全部ON。ただしZIP展開の建付けは維持し、`.gitmodules`をZIPから読み取って各submoduleのURL+ブランチ名を割り出し、それぞれ個別にZIPダウンロードする「疑似submodule解決」を実装する。**
  「ZIPからビルドする」という原文の説明を壊さずに済みますが、`.gitmodules`に書かれた`branch`は追跡ブランチ名であり、親リポジトリが実際に固定しているコミットそのものとは厳密には一致しない可能性があります(ズレても実用上は無視できる差分になることがほとんどとは思いますが、100%の再現性は保証できません)。
- **案C: 標準搭載分(dr_mp3/dr_flac/stb_vorbis、PNG/JPEG/BMP等)はZIP展開のみで賄い、dav1d等の重量級コーデックが必要な追加形式(AVIF, JPEG-XL, libmpg123, FLAC本家, Opus, MOD, MIDI等)だけはaptのシステムライブラリを使う。**
  ビルド時間・ディスクを最も抑えられますが、「全機能を有効化しろ」というご指示には部分的にしか応えられません(aptで賄う部分は"vendored"ではなく"システムライブラリ利用"になる)。

私の意見としては、要件が「全機能を持たせたSDL環境を全自動で作る」ことである以上、**案Aが最も筋が通っている**と考えます。「ZIP展開」という記述は元々「submoduleの存在を知らない状態で書かれた実装詳細」であり、目的(全自動・全機能・インクリメンタル)を達成する手段は変えてよい部分だと思うからです。ただし最終判断はお任せします。

## 5. ccacheについて

**何が起きるか**: ccacheはコンパイラ呼び出し(`gcc`/`g++`)をラップし、「同一ソース+同一コンパイルオプション」のコンパイル結果(オブジェクトファイル)をハッシュ化してキャッシュディレクトリ(デフォルト`~/.cache/ccache`、環境変数`CCACHE_DIR`で変更可能)に保存する仕組みです。次回以降、同じ入力ならコンパイルをスキップしてキャッシュからコピーします。

**ディスク使用量**: デフォルトの上限は5GB(`ccache -M`で変更可能)。ただしSDL本体+4拡張ライブラリ程度の規模なら、実際に使うのはおそらく数百MB程度に収まります(全機能ON構成だとdav1d等も含むためもう少し増える可能性はあります)。

**インクリメンタルビルドとの関係、効果の差**:
- 今回のスクリプトの「インクリメンタルビルド」は「同じバージョンなら再ビルドしない(丸ごとスキップ)」という粒度です。つまり**バージョンが1つでも上がったら、そのライブラリは全ファイルを再コンパイル**します。
- ccacheは「ソースコードの内容が変わっていないファイル単位」でキャッシュが効くため、**バージョンアップ時に変更が少ないファイル(多くのプロジェクトは大半のファイルが毎回微修正程度)は、たとえバージョンが変わっても再コンパイルされずキャッシュヒットします**。これは今回のインクリメンタルビルドの粒度(バージョン単位)ではカバーできない部分です。
- 効果の大きさはプロジェクト次第としか言えませんが、一般的にccacheは「変更のない再ビルド」で数倍〜数十倍速くなることが多いです(仕組み上、コンパイル自体をスキップしプリプロセス後のハッシュ比較+ファイルコピーだけになるため)。

**RAMディスク運用との整合性についての懸念、その通りだと思います**: `CCACHE_DIR`をデフォルトのまま(`~/.cache/ccache`、通常ホームディレクトリ=SDカード等の実ディスク)にすると、おっしゃる通り「/tmp/で回避したはずのディスク書き込み」が発生し、目的と矛盾します。もし導入するなら**`CCACHE_DIR`も`/tmp/`配下(RAMディスク)に置く**べきです。ただしその場合はキャッシュ自体もRAMディスク上に載るため、再起動でRAMディスクが消えるとキャッシュも消え、効果は「同一起動セッション内での再ビルド高速化」に限定されます(それでも`clean`後の再ビルドや、バージョンアップ後の再ビルドには十分効くはずです)。

**結論としての私の意見**: 「/tmp/に置く」を前提にするなら、ccache導入によるデメリット(実ディスク書き込み)は無く、メリット(バージョン更新時の差分再ビルド高速化)だけを享受できるので、**導入をおすすめします**。ただし2GBのRAMディスクの残り容量次第では、ソース+ビルド成果物+ccacheキャッシュで容量を圧迫する可能性があるため、導入するなら容量監視(空き容量が閾値を下回ったら警告、または古いccacheエントリを`ccache -c`でクリーンする仕組み)もセットで用意すべきと考えます。
